Interview one-pager

SetQuant

SetQuant tracks insider trades filed with Thailand’s SEC and scores every executive on what their own buying and selling actually returned. One engineer. When someone says “walk me through your architecture”, draw this and nothing more:

The two paths

read is live and stateless · write is batched and offline

Read — every page view

Vercel serves a client-rendered Next.js app. From there the browser makes two independent calls: SWR hits the Go API on Cloud Run for filings and CEO scores, and Next.js’ own /api routes proxy Yahoo Finance for candles and index quotes, cached at the edge for an hour. The Go API is read-only — six GET endpoints, no writes, no session, no cache layer.

Write — once a night

A GitHub Actions cron at 14:00 UTC (after the SET close) drives headless Chrome through the SEC’s filing pages, parses the HTML table with pandas, converts Buddhist-era dates, and bulk-loads sec_filings. A second script pulls a year of prices from yfinance and upserts ceo_scores. Nothing in a request path ever writes.

Follow-ups they’ll ask

the answers the diagram is set up to invite

Why does the browser call Go directly instead of proxying through Next.js?

Because it saves a hop, and I decided the cost was acceptable. NEXT_PUBLIC_API_URL is inlined at build time, so the client fetches Cloud Run straight from the browser rather than paying a round trip through a Vercel function. The price is a CORS policy on the Go side, which is currently * — fine for a public read-only API, but the right follow-up is to pin it to the Vercel origin. It also means the API URL is public, which is only safe because the API is read-only.

Why truncate and reload instead of an incremental upsert?

The source has no stable row identifier. The SEC pages are rendered HTML with no filing ID I can key on, so an upsert would need a synthetic key over (symbol, name, trade date, volume) and would still drift when the regulator amends a filing. A full reload is ~4 MB, runs in minutes, and is idempotent. The real cost is a window during the reload where readers see an empty table — the honest fix is to load into a shadow table and swap.

Why Cloud Run rather than the usual PaaS?

Region and scale-to-zero. asia-southeast1 puts the API a few milliseconds from Thai users and from Neon, and the service costs nothing while idle. The deciding factor was gcloud run deploy --source: it builds the existing Dockerfile server-side, so there is no pipeline YAML, no registry login, and no build config in the repo at all.

Where does the scoring logic actually live?

In the pipeline, not the API. calculate_scores.py computes mark-to-market returns per executive per symbol — every buy and sell valued against current price, filtered for zero-volume and off-market-price filings — and writes the result to ceo_scores. The Go API just selects and orders. Every request is a single indexed read, and the expensive work happens once a night.

What breaks first?

The scrape. It is Selenium against someone else’s markup, so a layout change on the SEC site breaks ingestion silently — the app keeps serving yesterday’s data with no alarm. That is the first thing I would instrument: a freshness check on max(filing_date) that fails the workflow rather than the page.

What’s in the repo but not on the diagram?

A Twitter bot. twitter.go formats a daily insider-trade post and there are internal endpoints behind a shared-secret header to trigger it. It is deliberately not deployed — no credentials in production — so it is not part of the architecture I would claim to run.
